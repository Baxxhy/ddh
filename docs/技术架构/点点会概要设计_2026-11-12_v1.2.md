## 1. 项目概述

### 1.1 背景与定位

医院挂号、公交乘车和移动支付已成为常见的手机操作。部分老年人会接打电话、发送消息，却不熟悉这些多步骤流程，也担心选错信息、产生真实预约或资金损失。图文教程和视频能讲解步骤，但难以让用户安全地动手尝试、在出错时立即获得针对性帮助。

点点会是一款面向老年人的智能手机情景模拟练习软件。用户在模拟界面中亲自点击、选择、核对和确认；点错后可返回、修改或重新开始，并可获得文字和语音指导，逐步学会独立完成常见操作。

### 1.2 第一版目标

1. 提供三个完整、可操作的生活场景：医院预约挂号、公交乘车码、扫码支付。
2. 每个场景都让用户亲自完成关键步骤，并得到清晰的操作结果。
3. 允许误触、选错、返回、修改和重新练习。
4. 用户随时可以请求与当前步骤相关的 AI 文字指导，并朗读提示。
5. 使用大字体、大按钮、简洁文案和稳定的导航，降低阅读与触摸难度。
6. 所有业务信息均为模拟数据，不接入真实医院、公交或支付系统。

### 1.3 用户与范围

主要用户为具备基本智能手机点击能力，但不熟悉挂号、乘车码和扫码支付流程的老年人。第一版打开网页即可选择场景和开始练习，无需注册或登录。

第一版仅包含三个场景及其必需的公共能力：模拟点击与输入、步骤反馈、返回与重试、AI 求助、文字提示和语音朗读。暂不建设账号登录、跨设备同步、学习档案、历史记录、学习进度统计、复习推荐、家属端、管理后台、额外学习模式或其他生活场景。

### 1.4 应用形态

第一版只开发 **React + TypeScript + Vite 的移动端优先响应式 Web 应用**。手机竖屏是主要使用场景，用户在手机浏览器中直接访问；桌面浏览器用于兼容访问和本地调试。页面从手机应用的单列任务流、导航和触控方式出发设计，不把传统 PC 网站布局简单缩小。前端与 FastAPI 后端独立运行，通过 HTTP API 通信。

## 2. 用户可使用的功能

技术模块不列为用户功能。下表中的每项功能均应在界面上有可操作入口和明确结果。

| 用户功能 | 用户操作 | 系统反馈 |
| --- | --- | --- |
| 选择练习场景 | 点击医院挂号、公交乘车码或扫码支付 | 展示该场景的模拟任务与开始入口 |
| 动手完成练习 | 在模拟手机界面中点击、选择、输入和确认 | 展示对应模拟页面及当前步骤状态 |
| 返回与修改 | 点击返回或修改已选信息 | 回到可修改的步骤，保留适当的已选内容 |
| 错误后重试 | 选错入口、信息或模拟扫码失败后重试 | 说明当前问题和可执行的下一步，允许继续操作 |
| 请求帮助 | 点击“我需要帮助”或输入与当前步骤相关的问题 | 展示简短、具体的文字指导 |
| 朗读指导 | 点击“朗读”或“停止朗读” | 语音播报或停止当前指导，文字始终可见 |
| 重新练习 | 点击“重新开始” | 重置当前场景，从第一步重新操作 |
| 查看模拟结果 | 完成场景最后一步 | 展示模拟成功结果，并说明没有产生真实业务记录或资金交易 |

### 2.1 统一交互原则

- 每个场景先给出一句清楚的练习任务，再进入模拟界面。
- 当前页面始终有明显的“模拟练习”标识；任务完成页再次说明结果仅在练习环境中有效。
- 用户必须亲自执行关键动作，系统和 AI 不代替点击、选择或确认。
- 错误操作不导致真实后果，也不让用户陷入无法返回的页面。
- 返回、求助、重新开始的位置在三个场景中保持一致。
- 提示先指出下一步，再按用户需要解释原因；避免一次展示过多文字。
- 不要求输入身份证号、银行卡号、支付密码等真实敏感信息。

## 3. 三个场景的业务流程

### 3.1 医院预约挂号

**练习目标：** 熟悉查找预约挂号、选择医院与科室、核对时间并确认的基本流程。

**模拟任务：** 使用演示资料，在模拟医院完成一次指定门诊的预约。任务所需医院、科室、医生和时间由场景演示数据给出，均不代表真实号源。

| 顺序 | 用户操作 | 页面与结果 |
| --- | --- | --- |
| 1 | 进入模拟医疗服务应用，点击“预约挂号” | 展示医院列表 |
| 2 | 查看并选择医院 | 展示该医院的模拟科室 |
| 3 | 查看并选择科室 | 展示医生或门诊类型 |
| 4 | 选择医生或门诊类型 | 展示可选就诊日期与时间 |
| 5 | 选择日期和时间 | 展示预约信息核对页 |
| 6 | 核对医院、科室、医生、时间，必要时返回修改 | 信息更新后再次展示核对页 |
| 7 | 点击“确认模拟预约” | 展示“模拟预约成功”及已选信息 |

选错医院、科室、医生或时间时，可以返回对应列表修改；误入其他模拟页面时可以正常返回。用户在任一步都能请求帮助。成功页必须明确说明没有产生真实挂号记录。

### 3.2 公交乘车码

**练习目标：** 熟悉在手机应用中查找、打开和使用公交乘车码。

| 顺序 | 用户操作 | 页面与结果 |
| --- | --- | --- |
| 1 | 进入模拟生活服务应用，找到“出行” | 展示交通服务入口 |
| 2 | 进入交通服务并选择“公交” | 展示公交服务页面 |
| 3 | 点击“乘车码” | 展示明显标注为模拟的无效二维码图形 |
| 4 | 将模拟乘车码对准虚拟扫码器 | 展示模拟扫码反馈 |
| 5 | 扫码成功 | 展示“模拟乘车成功” |

点击其他服务入口或误入地铁乘车码时可以返回并切换至公交；模拟扫码失败后可以重新展示乘车码并重试。二维码不得包含可用于真实乘车或支付的有效凭证。

### 3.3 扫码支付

**练习目标：** 熟悉打开扫一扫、识别收款方、核对金额与确认付款的步骤，建立先核对再确认的习惯。

| 顺序 | 用户操作 | 页面与结果 |
| --- | --- | --- |
| 1 | 进入模拟支付应用并点击“扫一扫” | 展示模拟扫码界面 |
| 2 | 扫描演示收款码 | 展示演示商户与待填写金额 |
| 3 | 输入任务指定的模拟金额 | 展示付款信息核对页 |
| 4 | 核对商户、金额，必要时返回修改 | 核对信息随修改更新 |
| 5 | 点击“确认模拟付款” | 展示“模拟支付成功”及演示交易信息 |

选错入口、演示收款码或金额时可返回修正；金额无效时应明确说明问题并允许重新输入。确认前必须显示商户与金额。不得要求输入真实支付密码、银行卡信息，也不得发起真实支付请求。成功页明确说明没有发生资金交易。

## 4. 页面与交互设计

### 4.1 页面结构

1. **场景选择页：** 只展示三个场景，使用清楚的名称和大按钮；无需登录入口。
2. **场景任务页：** 简要说明本次目标、模拟属性与“开始练习”。
3. **模拟练习页：** 主区域显示可点击的模拟手机界面；固定位置提供返回、求助、朗读与重新开始。文字指导与当前操作同屏可见。
4. **模拟结果页：** 展示本次模拟结果、关键已选信息、“再练一次”和“选择其他场景”。

AI 求助在练习页内展开，不为其增加独立页面。第一版没有“我的学习”、学习进度或历史记录页面。
页面在手机竖屏下采用应用式单列布局和稳定的操作区；桌面端保持同一任务顺序与交互，不改造成传统 PC 后台或多栏网站。

### 4.2 适老化要求

- 正文和操作文字使用足够大的字号；主要按钮有较大的触控区域和间距，降低误触。
- 文字与背景保持清晰对比，不只靠颜色传达成功、错误或当前步骤。
- 文案使用熟悉的中文，例如“返回上一步”“再试一次”“朗读提示”。
- 一屏只呈现当前决策必需的内容；保持导航和操作位置稳定。
- 支持键盘焦点、清楚的焦点样式与可访问名称；语音不可用时文字指导仍完整可用。
- 手机竖屏优先，同时保证桌面浏览器可用；避免横向溢出和遮挡按钮。手机端主要操作目标建议至少 60×60 CSS px，正文默认 20–22 CSS px，支持大字模式及 200% 文字放大。

## 5. 系统技术架构

技术用于支撑上述用户功能，不作为面向用户的独立功能入口。

| 层次 | 技术 | 职责 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 构建移动端优先的响应式 Web 应用，渲染场景、模拟页面和指导内容；处理用户点击、输入、返回与朗读 |
| 后端 API | Python、FastAPI | 校验输入，管理练习会话，执行场景规则，提供指导接口 |
| 数据存储 | MySQL | 保存场景配置、演示数据及当前练习所需的临时状态 |
| 知识检索 | RAG 知识库 | 检索经整理的场景步骤、常见错误和安全提醒，为指导提供依据 |
| 指导编排 | LangGraph 单 Agent | 结合当前场景、当前步骤、用户问题和检索内容，生成受约束的指导 |
| 模型接入 | 可配置模型适配层 | 通过后端环境变量接收模型名称、地址与 API Key；不暴露给浏览器 |
| 语音 | 浏览器语音朗读能力或后续可替换的语音适配层 | 朗读当前文字指导，支持停止与重听 |

### 5.1 场景状态与确定性规则

三个场景均由可测试的步骤、合法动作、输入约束和转移规则定义。后端根据当前状态判断操作是否有效，更新模拟页面和结果；返回或重新开始由规则处理。AI 不能决定挂号是否成功、扫码是否通过、金额是否正确，也不能绕过确认步骤。

场景状态至少包含场景标识、当前步骤、当前选择或输入、可返回路径和本次交互反馈。第一版只需要当前会话；不建立跨设备身份，也不把练习过程作为长期学习档案。临时会话应设置过期清理策略。

### 5.2 AI 与 RAG 指导

用户请求帮助或操作出错时，后端向 LangGraph 单 Agent 传入场景、步骤、用户问题及已确认的操作状态。Agent 先检索与该步骤相关的知识片段，再生成简短中文指导，并校验输出是否只建议当前允许的安全操作。返回内容包含指导文字、来源标识和是否为模型生成的状态。

知识库首批内容仅覆盖三个场景的步骤说明、常见误操作和“模拟环境”安全说明。模型不可用、超时、返回空内容或校验失败时，使用经过维护的场景提示作为降级指导，并在界面上如实区分。指导只解释下一步，不代替用户操作，也不声称模拟结果真实有效。

语音朗读以同一份已展示的指导文字为输入，避免文字与语音内容不一致。浏览器不支持朗读时，显示清楚的不可用反馈。

## 6. 数据与接口设计

### 6.1 概要数据对象

| 对象 | 主要字段 | 说明 |
| --- | --- | --- |
| 场景配置 | 场景 ID、名称、版本、步骤、合法动作、演示数据 | 仅三个场景；业务规则和演示数据可追溯 |
| 临时练习会话 | 不可猜测的会话 ID、场景 ID、当前步骤、当前选择、过期时间 | 支持本次操作、返回和重试；过期后清理 |
| 知识片段 | 片段 ID、场景 ID、适用步骤、正文、版本 | 为 RAG 检索和指导来源标识服务 |

第一版不设计用户账号表、学习档案表、长期历史记录表或统计报表。演示商户、医院、医生、金额及二维码必须显著标记为模拟资料。

### 6.2 API 边界

| 接口职责 | 请求 | 响应 |
| --- | --- | --- |
| 获取场景列表与任务 | 场景 ID 可选 | 三个场景的名称、任务和可进入状态 |
| 开始练习 | 场景 ID | 临时会话 ID、初始页面与步骤 |
| 提交模拟操作 | 会话 ID、动作、必要输入 | 新步骤、页面数据、成功或错误反馈 |
| 返回或重新开始 | 会话 ID、操作类型 | 恢复后的步骤与页面数据 |
| 请求指导 | 会话 ID、可选问题 | 指导文字、来源、生成或降级状态 |

所有接口校验场景 ID、会话 ID、动作类型和输入长度；不能仅凭前端状态判定模拟业务成功。API 错误信息使用用户可理解的中文，不暴露密钥或内部异常详情。
本地开发时，Vite 开发服务器应允许同一局域网内手机访问，并将 `/api` 请求转发至独立运行的 FastAPI 服务；正式运行时由环境配置决定 API 地址。手机浏览器必须能经所访问的前端地址调用 API，不能依赖手机自身的 `localhost`。

## 7. 安全、可靠性与非功能要求

- 模拟系统不调用真实挂号、公交或支付接口，不生成有效支付码或乘车凭证。
- 不收集真实身份证号、银行卡号、支付密码；模型密钥只保存在后端环境变量。
- 服务端验证金额等输入，防止非法状态跳转；会话标识不可预测并设置过期时间。
- 练习操作失败后保留可恢复状态；AI 服务异常不影响三条模拟主流程。
- 三个场景的加载、成功、失败与空状态必须清晰；保持移动端触控与桌面端键盘可用。
- 不把模型推测当作真实医疗、交通或支付规则；知识资料需标注来源与版本。

## 8. 开发顺序与验收

第一阶段按[开发计划 V1.1](../开发记录/点点会开发计划_2026-11-12_v1.1.md)仅搭建项目基础、演示数据和可读取场景列表的接口与页面，不提前实现后续阶段的练习流程、AI 或语音。

### 8.1 开发顺序

1. 建立三个场景的任务、演示数据和可测试的状态转移规则。
2. 完成场景选择、任务、模拟练习和结果页面，以及统一的返回与重试交互。
3. 接入 MySQL 保存当前练习所需的临时状态，完成 FastAPI 接口。
4. 建立三个场景的知识片段，接入 RAG 与 LangGraph 指导，并实现异常降级。
5. 接入文字朗读，完成适老化、响应式与可访问性检查。
6. 验证三个场景的完整流程、典型错误和恢复路径，记录真实测试结果。

### 8.2 第一版验收标准

- 无需注册即可进入三个场景，每个场景均能从开始操作到模拟成功页。
- 用户可以在关键选择处故意选错、返回修改并重试；重新开始后状态正确重置。
- 医院挂号的结果展示模拟医院、科室、医生和时间；公交场景展示模拟乘车结果；支付场景在确认前展示商户和金额。
- 任一步都可请求与当前步骤相关的文字指导；可朗读、停止和重听；模型异常时仍有明确的可用提示。
- 全程不产生真实预约、乘车或资金交易，所有关键页面和结果页明确提示“模拟”。
- 在常见手机宽度与桌面浏览器上无关键内容遮挡、不可点击或横向溢出；键盘可完成主要操作。
- 手机竖屏界面呈现应用式单列任务流；本地同一局域网内的手机可打开前端并读取 FastAPI 提供的场景列表。
- 相关自动测试、类型检查、Lint 和构建检查通过；无法运行的检查如实记录。
